# Патчи безопасности для клиента goro

Серия из шести патчей к клиенту [kivutar/goro](https://github.com/kivutar/goro),
закрывающая находки аудита. Базовый коммит — `4dcf7e93c63bceb92c04225df90b1d6b8f074848`
(ветка `main`, 24.08.2026). Итого: 27 файлов, +1494/−108 строк, из них около
850 строк — регрессионные тесты.

## Модель угроз

Клиент обрабатывает два потока недоверенных данных, и все патчи касаются только их:

1. **Сеть.** Пакеты от login/char/map-сервера. Оператор сервера, к которому
   подключается игрок, полностью их контролирует.
2. **Игровые данные.** GRF-архивы, спрайты, карты, модели, текстуры и Lua-байткод
   (`.lub`), которые оператор раздаёт вместе с клиентом.

Go безопасен по памяти, поэтому речь идёт не об RCE, а об отказе в обслуживании,
неконтролируемых аллокациях, выходе за пределы каталога данных и утечке учётных
данных в логи. Единственный сценарий с исполнением кода — патч 0002.

## Что в патчах

### 0001 — сеть: рассинхронизированный поток рвётся, а не буферизуется

`Framer.Push` при неразбираемом потоке оставлял все байты в буфере и на каждом
новом чанке заново сканировал его целиком. Сервер мог наращивать память клиента
без ограничений и с квадратичной стоимостью. Теперь ошибка кадрирования
оборачивается в `ErrUnsyncedStream`, framer освобождает уже отвергнутые байты,
объём ожидающих данных ограничен 128 КиБ, а цикл чтения отключается вместо
бесконечных попыток. Отдельно: трассировочные логи больше не выгружают payload
пакетов с паролем (`0x0064`) и сессионным токеном (`0x0065`, `0x01FB`), а очереди
входящих пакетов и ошибок ограничены.

### 0002 — конфиг: `goro.ini` больше не подхватывается из текущего каталога

Запуск клиента из произвольного каталога читал найденный там `goro.ini`, а этот
файл мог задать `script.path` — путь к Lua-скрипту, который игра выполняет с
полной стандартной библиотекой. Это исполнение произвольного кода через подброс
файла в папку загрузок или на общий диск. Теперь конфигурация берётся только из
каталога пользователя или из явного `--config`, `script.path` принимается лишь
как флаг командной строки, а конфиг с паролем, доступный на чтение другим
пользователям, выдаёт предупреждение. Лог-файлы создаются с правами `0600`,
поскольку при трассировке в них попадают пакеты.

### 0003 — игра: эмблема гильдии и песочница для AI компаньонов

Эмблема гильдии приходит по сети zlib-потоком, и декодер принимал любые
заявленные размеры, так что 4 КиБ payload разворачивался в большую аллокацию.
Размеры проверяются до декодирования (предел 128×128 при штатных 24×24).
Скрипты AI хомункулов и наёмников читаются из каталога данных или GRF, поэтому
им закрыт доступ к `os.execute`, `io.popen`, `package.loadlib` и библиотеке
`debug`, а `io.open` не может выйти за пределы каталога данных.

### 0004 — res: проверка Lua-байткода до разбора и запуска

Четыре независимые проблемы в `res/lub.go`:

- счётчики прототипов принимались на веру, поэтому 20-байтный файл запрашивал
  аллокацию на 8 ГиБ или отрицательную длину;
- вложенность не ограничивалась, и несколько сотен килобайт вызывали
  `fatal error: stack overflow`, который нельзя перехватить через `recover`;
- резервный интерпретатор индексировал регистровый файл 9-битными операндами
  (до 511) при размере файла до 255+64 элементов — подтверждённая паника
  `index out of range [511] with length 72` на 75 байтах;
- самоссылающийся `OP_JMP` в 56-байтном файле вешал клиент навсегда.

Счётчики теперь сверяются с остатком буфера, вложенность ограничена 200 уровнями
(предел эталонного компилятора Lua), доступ к регистрам проверяется по границам,
исполнение идёт под дедлайном 2 с и бюджетом инструкций.

### 0005 — res: ограничение аллокаций по недоверенным заголовкам

Проверки вида `if count < 0` бесполезны при конверсии `uint32` → `int` на
64-битной системе, поэтому крошечные файлы вызывали фатальный
`runtime: out of memory`. Наблюдалось: 20-байтный ACT — попытка на ~112 ГиБ,
44-байтный GND — ~640 ГиБ, 18-байтный TGA — 16 ГиБ. Плюс в GRF `PackedSize` и
`AlignedSize` не были связаны между собой (`slice bounds out of range`), а
распаковка не ограничивалась заявленным размером (подтверждённая zlib-бомба
1029:1).

Записи GRF сверяются с реальным размером архива, `PackedSize` не может превышать
`AlignedSize`, распаковка ограничена. Счётчики ACT, GND, IMF, RSM, SPR, TGA и GR2
проверяются против остатка данных, размеры GAT больше не переполняются в обход
проверки на усечение, а менеджер ресурсов подтверждает, что итоговый путь остался
внутри каталога данных (до патча `ReadFile("../secret.txt")` читал файл за его
пределами).

### 0006 — зависимости

`golang.org/x/image` 0.43.0 → 0.45.0 и `toolchain go1.26.6` ради защиты от
переполнения рекурсии в `encoding/xml`: `clientinfo.xml` и таблица `pet_talk`
читаются из каталога данных. После обновления `govulncheck ./...` не находит
ничего.

## Как применить

```bash
git clone https://github.com/kivutar/goro
cd goro
git checkout 4dcf7e93c63bceb92c04225df90b1d6b8f074848
git checkout -b security-hardening
git am /path/to/docs/goro-security-patches/*.patch
```

Если основная ветка ушла вперёд и `git am` конфликтует, полезен трёхсторонний
режим: `git am -3`. Разрешить конфликт и продолжить через `git am --continue`.

## Проверка

```bash
CGO_ENABLED=0 go build -tags nofakecgo ./...
CGO_ENABLED=0 go test -tags nofakecgo -count=1 ./...
gofmt -l .
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

На момент подготовки серии: сборка проходит, все 14 пакетов с тестами зелёные,
`gofmt` чист, `govulncheck` — «No vulnerabilities found». Тесты с реальными
данными пропускаются, пока не задан `GORO_DATA_DIR`.

Каждый новый тест проверялся на способность поймать исходный баг: файлы
откатывались к состоянию до патча, и тест падал именно с тем симптомом, который
описан в аудите.

## Что осталось за рамками

- `game/bot.go` исполняет Lua из `--script` с полной стандартной библиотекой.
  Это осознанно: флаг задаёт сам игрок, а после патча 0002 конфиг-файл его
  подменить не может.
- Пределы `grfMaxUnpackedSize` (256 МиБ на запись) и `maxParsedImageDimension`
  (8192) заметно выше всего, что встречается в официальных данных, но приватный
  сервер с очень крупными ассетами их заметит. Оба значения заданы одной
  константой.
- Патч 0005 отклоняет GRF целиком, если таблица объявляет запись за пределами
  файла, тогда как раньше ошибка возникала только при чтении этой записи.

## Заметки к завтрашнему запуску сервера и клиента

Порядок, в котором удобно поднимать связку rAthena + goro:

1. Собрать rAthena, создать базу, накатить `sql-files/main.sql` и
   `sql-files/logs.sql`.
2. В `conf/char_athena.conf` и `conf/map_athena.conf` выставить внешние адреса,
   иначе клиент получит `127.0.0.1` и не подключится с другой машины.
3. `PACKETVER` в rAthena должен соответствовать `packet.clientdate` в goro. Клиент
   ориентирован на пре-ренейвал 2008 года, таблица пакетов — `PacketLengths2008()`.
4. Создать тестовый аккаунт в таблице `login`.
5. Каталог данных goro: распакованный GRF или папка `data`. Путь задаётся через
   `--data-dir`.
6. После патча 0002 `goro.ini` рядом с бинарником больше не читается. Нужный
   конфиг положить в каталог пользователя (`os.UserConfigDir()/goro/goro.ini`) или
   передать `--config path/to/goro.ini` явно.
7. Пароль лучше передавать флагом `--password`, а не хранить в конфиге. Если он
   всё же в файле — права `0600`, иначе клиент предупредит.
8. Для диагностики протокола: `--net-trace` вместе с `--log-level debug`. После
   патча 0001 пароль и сессионный токен в дамп не попадут.

Если на этом пути что-то не сойдётся, полезно начать с `--log-level debug`:
ошибки кадрирования теперь явно называют неизвестный опкод и рвут соединение
вместо тихого накопления мусора в буфере.
